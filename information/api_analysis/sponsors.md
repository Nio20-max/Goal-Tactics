# Sponsors API — SponsorController

> **Source:** `src/GoalTactics.Api/Controllers/SponsorController.cs`
> **Route prefixes:** `api`, `api/Sponsor`

---

## Global Notes

- All requests use **HTTP POST** with `Content-Type: application/json` (legacy Xamarin design).
- Base `RequestObject` has legacy fields: `signature`, `token`, `locale`, `utcOffset`, `culture`, `platform` — accepted but ignored.
- Base `ResponseObject` has: `success`, `message`, `status` (1 = OK / 2 = Error), `errorMessage`, `punishment`.
- Authentication via **Bearer JWT** in the `Authorization` header.
- Legacy Xamarin client also sends the token in the request body and as a query param `?access_token=`.
- Legacy routes existed at `/GameEngine/*` (nginx rewrites to `/api/`).
- The Xamarin client (v1.2.4) uses both old `/GameEngine/*` and new `/api/*` URL patterns.

---

## Authentication

**All endpoints require `[Authorize]` — a valid Bearer JWT must be provided.**

## Endpoints

### POST `/api/GetSponsorOffers`

| Property | Value |
|---|---|
| **Alias** | `/api/Sponsor/GetSponsors` |

#### Purpose

Returns available sponsor offers for the authenticated user's team.

#### Request — `RequestObject`

Standard base request object.

#### Response — `SponsorOffersResponse`

```json
{
  "success": true,
  "status": 1,
  "sponsors": [
    {
      "id": "sponsor-guid",
      "name": "MegaCorp Industries",
      "bonus": 50000,
      "duration": 5
    },
    {
      "id": "sponsor-guid-2",
      "name": "SportsDrink Co.",
      "bonus": 30000,
      "duration": 3
    }
  ]
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | `string` | Sponsor offer identifier. |
| `name` | `string` | Sponsor display name. |
| `bonus` | `decimal` | Per-matchday income bonus from this sponsor. |
| `duration` | `int` | Contract duration in matchdays. |

#### Implementation Note

Sponsors are **generated deterministically** by the `SponsorService` — there is no standalone sponsor entity in the database. Offers are computed based on team attributes (strength, league position, fan count, etc.).

## Security Notes

- All endpoints require `[Authorize]`.
- `AcceptSponsor` should validate that the sponsor offer is still valid (hasn't expired or been altered since generation).
- Since sponsors are deterministically generated, the server must validate the sponsor ID against the current generation state — a stale ID from a previous generation cycle should be rejected.

## Versioning

- Route aliases: `GetSponsorOffers` ↔ `GetSponsors`.

## Potential Pitfalls

- **No standalone sponsor entity** — sponsors are generated by `SponsorService` deterministically. This means:
  - Sponsor IDs may be regenerated each time offers are requested.
  - The client should not cache sponsor IDs across sessions.
  - `NegotiateSponsor` and `AcceptSponsor` must be called with a sponsor ID from the current `GetSponsorOffers` response.
- The `NegotiateSponsor` → `AcceptSponsor` flow is a two-step process; the client calls negotiate first, then accept.
- Sponsor bonus amounts scale with team progression — higher-ranked teams get better offers.
- Only one active sponsor can be held at a time (or a limited number) — the server must enforce this constraint.
